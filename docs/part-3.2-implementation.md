# Peyce Part 3.2 implementation

Peyce is pronounced **peace** (/piːs/). This milestone turns the Part 3.1 design into a single-user localhost Vue → FastAPI → SQLite coursework application for fictional use. It is not a deployed support service. The archived `submissions/3.1/` report and its immutable evidence remain historical; the pronunciation correction applies to the current product.

The supplied overview requires at least one usable chosen skill, relevant real-model contribution, persisted conversation/session history, complete exercise timing, independent support, and failure/leave evidence. [Verification](part-3.2-verification.md) records the complete local breathing/SQLite flow, 88.1449-second scripted sequence, four simulated viewports and actual failure/leave checks. **The genuine model contribution remains unmet: two authorized attempts returned fallback, including HTTP 401; a usable server-local credential and a successful validated UI contribution are required.** An implemented adapter or validated mock cannot fulfill it. Instructor acceptance of button-led structured conversation remains unresolved.

## Saved records and why they exist

Saving is an explicit fictional-use choice before session entry. In-memory use remains available without it. No answer history is stored in browser storage; session storage retains only an active saved-session ID for best-effort interruption recovery. The normal ignored database is `backend/.runtime/peyce.sqlite3`; tests create isolated temporary databases. Local records remain until the history clear action is explicitly confirmed. Credentials, environments, SQLite/WAL/journal files and dependencies are ignored by Git.

| SQLite record | Retained information | Purpose |
| --- | --- | --- |
| `sessions` | UUID; created/updated/ended timestamps; current revision/status/exercise; explicit visual preference; schema/question/content/policy versions; fictional-local-coursework context; current snapshot and result | Return the latest acknowledged state and avoid presenting ordinary history as a clinical profile. `ended_at` describes an observed terminal transition; interruption does not invent a completion time. |
| `revisions` | Immutable snapshot, deterministic result and timestamp for each committed revision | Explain Back/edit/choice changes and identify superseded offers without replacing their audit history. |
| `turns` | Assistant question and user answer/explicit skip; exact question/answer identity; sequence, revision, version, source and timestamp | Separate an explicit skip from an absent/unreceived write. A later snapshot preserves earlier turns as superseded; the view shows current answers once and places repeated historical snapshots under an Earlier revisions disclosure. |
| `operations` | Unique operation UUID, session/revision/kind, exact request and saved response | Return an idempotent receipt for a retry and reject the same ID reused for a different action. |
| `lifecycle` | Unique event UUID; kind/cause; session-relative monotonic offset; active elapsed time; revision and saved timestamp | Distinguish instruction/start/pause/resume/support/stop/completion/Finish actions and retain one logical completion across retries. |
| `explanations` | Request/session/revision; actual mode/model; prompt/question/policy versions; reason code; outcome/validation; approved fragment/reference IDs; rendered text; obsolete flag and timestamps | Make the optional acknowledgment traceable to the actual committed selections, separately from raw user turns. Invalid provider prose and credentials are not stored. |
| `live_budget` | Persistent outbound-attempt count and reserved spend | Prevent replay/restart/history clearing from resetting the live-call guard. This is a bounded coursework guard, not proof of exact provider billing. |

Schema version is `PRAGMA user_version=1`. Initialization accepts an empty/version-1 database and refuses an unknown version instead of resetting it. Explicit history clearing cascades session-related rows but preserves the live-attempt guard. New revisions must advance; a new session begins at revision 1. Repeated immutable lifecycle events are deduplicated, and a conflicting event rolls back the entire snapshot transaction.

Public session/provider evidence is deliberately curated from the real API plus read-only SQLite inspection. The primary database has 71 turn rows; the export retains 11 current/validated acknowledgment rows and explains the 60 omitted repeated superseded structured rows with SQL counts by revision/source/role. Exact committed ready-turn context is separately retained for each explanation attempt. Unique lifecycle, timing, versions, current choice/result and safe model receipts are preserved. These artifacts are faithful selected evidence, not unmodified full database/API dumps; runtime databases remain private/ignored.

## State and failure contract

The ordinary path is `checkin → choice/ready → active → completed → finished`; direct entry begins at choice. `completed` follows the final exercise step; `finished` additionally records the planned closing Finish action. A partly used exercise becomes `stopped` through deliberate Stop. Finish after Stop preserves the stopped status. Leaving before starting is a stopped/left session rather than completed exercise evidence.

Only acknowledged writes display Saved. A failed write displays Not confirmed saved and preserves exercise, Stop and support. Retries keep their operation IDs so an accepted response lost in transit cannot duplicate a logical action. An older answer revision cannot overwrite a newer one. The current API/data contract is in [part-3.2-api-contract.md](part-3.2-api-contract.md).

Restart reconciliation changes previously `active`/`paused` records to `interrupted`, preserving already stopped/completed/finished records. Pagehide and session-ID recovery are best effort; neither can guarantee delivery during a crash or prove when the user left. A hard close without successful reconciliation may leave an active record until restart/recovery. An interrupted label is an inference about unfinished interface use, not a confirmed Stop or clinical judgment.

The ready screen receives the deterministic rule result without waiting for a provider. A separate explanation request is eligible only for its unchanged ready session/revision. A display generation, abort signal and response identifiers prevent Back, direct choice, Stop, switching, new session or late work from restoring an abandoned result. The server rechecks current revision/status and retains an obsolete receipt when appropriate. Replaying a pending or finished request ID does not call the provider again.

Observed integration checks exercised an initial injected database failure before revision 1 and successful later retry, read failure/recovery, invalid/provider/timeout/late mock responses, an actual rejected provider call, explicit Stop, a real browser reload, and an actual owned-backend process outage. During the outage local support and an unsaved direct Start/Stop/Finish still worked. Actual reload left the saved exercise interrupted without inventing completion, and the completed primary record/timing survived backend restarts. Fault injections are identified separately from actual runtime rejection/process stoppage.

## Constrained conversation and live boundary

The server sends the current received assistant-question/user-answer-or-skip turns, deliberate exercise/current choice, the approved deterministic result and eligible current question IDs. It sends no older session or hidden score. The provider may select only `reason_code`, `opening_id` (`reflect`/`notice`), up to two eligible `reference_ids`, and `closing_id` (`choice`/`change`). The application requires the exact approved reason, rejects extra/unknown fields and unsupported/skipped references, inserts exact selected answer labels, and caps the rendered acknowledgment at 240 characters. Different valid selections/references affect the displayed copy.

This construction gives the model a small, inspectable conversational contribution. Its cost is limited expressiveness and uncertain added value over deterministic copy. It is not unrestricted counseling and does not establish semantic/clinical safety. Invalid, empty, timed-out or failed output retains local approved rule copy, with a separately recorded fallback subtype; raw provider prose is never displayed as a fallback.

The authorized free model's catalog does not advertise native `response_format` support. The adapter therefore supplies the exact JSON schema/enums and an example in its system context rather than sending an unsupported API parameter. **The application enforces the strict construction boundary**, after JSON parsing and before display/persistence of approved wording; it does not claim that the provider guarantees structured output. This compatibility change may increase fallback frequency, but does not relax the accepted fields, current-answer references, copy grammar or zero-price/provider restrictions.

The human's later explicit authorization overrides the master prompt's five-attempt ceiling for this run: **OpenRouter, exact `nvidia/nemotron-3.5-lightning:free`, zero dollars, maximum ten outbound attempts**, including failures. The configured adapter fails closed for a different model, missing credential/approval/pricing verification, nonzero prices or exhausted attempts. Requests disallow paid provider fallback and cap input/output/time. The safe configuration/pricing record is `docs/evidence/3.2/openrouter-configuration.json`. That record alone is not a successful live response; actual success/failure and count belong in verification evidence. The server-local `.env` is ignored and never sent to Vue or published.

## Timing and findings translated into decisions

Breathing retains a single monotonic phase clock: four seconds inhale, six seconds exhale, six cycles, no hold. The full measured sequence begins when ready instructions are visible and ends at the closing Finish action. It includes reading, Start/Finish decisions, transitions, optional decisions and imposed delays. Active pacing is 60 seconds; it is not the full sequence duration. `SequenceTimer` records raw span and the union of explicit user-pause/support intervals; background time is counted. Server validation checks the arithmetic and corresponding instruction/Finish events. [Verification](part-3.2-verification.md) supplies the actual browser measurement and assumptions.

| Finding → decision | Alternative/cost | Actual check and limit |
| --- | --- | --- |
| R1: measure first instructions through Finish, retain six full cycles | A timer constant is simpler but omits reading/closing time | Actual uninterrupted browser sequence: 88.1449 seconds, no exclusions, entry/check-in separate. Unit/API checks verify arithmetic; the scripted result does not establish natural human timing or benefit. |
| R2/D4: support content and control live in Vue | Provider/API delivery would be easier to centralize but could fail with remote work | Actual provider rejection, injected database/model failures and stopped-backend checks retained support/exercise access. Dialog focus/pause/return were observed; no monitoring or crisis classifier exists. |
| R3/R4: direct current choice/refusal/unknown and Stop outrank suggestions | Automatic personalized routing would reduce clicks but invent authority | Versioned routing/regression tests, stale-reply/replay and explicit Stop/interruption persistence checks. The rule remains an unvalidated design heuristic. |
| D1/D2: retain one-task screens and quiet timing | A single large chat/dashboard adds competing decisions | Four actual simulated laptop/mobile viewports and loading/fallback/error/history states were inspected, with history and decoration refinements. Faces, response time and history do not detect distress. |
| D3: button-led turns and private grounding noticing | Less disclosure/expression than free text | Exact turns/skips are inspectable in SQLite/history. Structured turns still demand reading and instructor interpretation remains open. |
| D5: opt-in local history and explicit balloon preference | Useful continuity introduces storage and clearing work | Real SQLite history/clear/restart checks; no production retention, encryption, account or security claim. |
| D6: neutral ending and restrained local/model copy | Less expressive generated language | Bounded phrase validation and retained original assets. Appearance is not evidence of persistence correctness or clinical readiness. |

The instructor study summary (15 patients, 13 clinicians, 15 prototype evaluations, 150 participant-task combinations) is distinct from the 2020 JMIR study. Its mention counts are not effect sizes, and neither validates Peyce's matching policy. [Research ledger](research.md) retains access, licensing and inference limits. No protected STAI items, datasets, training, clinical profiles, production accounts or Part 3.3 evaluation are added.
